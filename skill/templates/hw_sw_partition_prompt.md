# 提示词工作流：从算法描述推导软硬件划分

**类型**：提示词模板（prompt workflow）
**适用场景**：拿到一个算法（FFT、mel 频谱、滤波、卷积、检测后处理等），需要决定哪些步骤
放 PL（HLS/RTL）、哪些放 PS（Python/C），并给出接口与预期收益。
**不适用**：算法本身还没定、或已经明确全部放软件的场景。

---

## 模板（可直接复制给大模型）

```
你是 FPGA 软硬件协同设计工程师。请分析下面的算法，逐步完成软硬件划分。

算法描述：
{把算法写成有序步骤，每步说明输入/输出形状与数据类型}

目标平台：
- 器件 {xc7z020 / xczu3eg / ...}，可用资源 {LUT __ / DSP __ / BRAM __}
- PL 时钟 {100 MHz}，PS 主频 {650 MHz}，PS 侧可用库 {numpy / OpenCV / ncnn}

对每一步输出：
1. 计算量：乘加次数、每元素访存次数
2. 并行度：能否沿哪个维度并行、能否流水、是否需要跨迭代依赖
3. 数据依赖：是否需要前一步完成全部结果
4. 控制复杂度：循环层数、条件分支、变长循环
5. 数值要求：是否需要浮点、定点可行性、位宽估计

然后给出：
- 划分建议表（步骤 | 放 PL/PS | 理由 | 预估耗时）
- 接口定义：每次传输的数据量、方向、频率、是否需要 DMA、是否需要乒乓缓冲
- 预期加速比与它的计算依据（基于什么假设，不要只给一个数字）
- 该划分最可能失败的地方，以及对应的验证方法
- 如果 PL 侧收益不明显（<2x），明确说明"不值得上硬件"，并给出理由
```

## 填写示例（本项目真实分析）

输入：2 s 音频（64000 样本 @32 kHz）→ 64×201 mel → 3 层 CNN → 1 个 logit。

| 步骤 | 放哪 | 理由 | 实测/估算 |
|------|------|------|-----------|
| 分帧+加窗 | PS | 纯内存搬运，numpy 向量化已足够 | 几 ms |
| 1024 点 FFT ×201 帧 | PS（未搬） | 高并行但流水开销大，工程量不划算 | ~数百 ms |
| 功率谱 / mel 滤波矩阵乘 | PS（未搬） | 同上 | 与 FFT 合并在 PS |
| **conv1（3×3，16 输出通道）** | **PL HLS GEMM（已实施）** | im2col 后是规则 GEMM（M=12864 K=9 N=16），定点 Q12，DSP 友好 | HLS 核 ap_done **6.7 ms**（repeat 5） |
| conv2 / conv3 / maxpool | PS | 层间依赖强、模型小，numpy 已够 | 与 rest_forward 合并 |
| FC / sigmoid | PS | 逻辑简单 | <1 ms |

结论与取舍（已落地与未落地分开写，避免"分析结论"被当成"实测加速比"）：

- **已实施**：conv1 通过 im2col 转成 GEMM，用 Vitis HLS 综合成 `gemm_top` 核，
  PS 侧三路 DMA（A/B 进、C 出）喂 Q12 定点数据。板端端到端实测：
  硬件 conv1 输出分数 **0.997878** vs numpy 全浮点 **0.997876**，
  conv1 输出 205824 点最大误差 **0.001838**（容差 0.02，0 点超差），判定 PASS。
- **未实施（被放弃的候选）**：FFT+mel 整个搬到 PL。模板当时给出的"20×"是分析估算，
  不是实测；实际评估后认为 AXI-Stream 乒乓缓冲 + 定点精度验证的工程量，
  相对 A9 上 mel 计算的延迟收益不划算，留作后续工作。
- **数字口径提醒**：6.7 ms 只是 HLS 核 `ap_start → ap_done` 的纯计算时间，
  **不含** im2col、Q12 量化、DMA 传输、cache flush/invalidate、反量化的时间。
  完整"硬件 conv1 端到端 vs numpy conv1 单独"的公平加速比，需在板子上分别计时
  （本项目待补，见 `skill/verification/board_checklist.md`）。不要把 6.7 ms
  直接和 numpy 整网 0.497 s 相除声称"74× 加速"。

## 使用方法

1. 先把算法步骤写清楚（不要给公式图片，写成有序步骤）。
2. 填好目标平台与可用资源（不知道就写"待确认"，模型会据此给出保守估计）。
3. 把模板 + 算法一起给模型。
4. **逐条核对模型给的"预期加速比"**：要求它给出计算依据；只有能算出来的数字才写进报告。
5. 用 `tools/vivado_report.py` 记录优化前后资源，用 `tools/golden_compare.py` 比对 PL 与
   软件参考的输出，把"加速比"变成可复现的两个数字（延迟 + 资源）。

## 已验证效果

在本项目的 mel + CNN 分析上，该模板产出了完整的分步划分表与接口数据量估算，
并给出两类结论：

- **被放弃的候选**：FFT+mel 整体搬 PL（分析估算 20×，但工程量不划算，未实施）；
- **已落地的划分**：conv1 im2col 成 GEMM，PL HLS 核 + PS 三路 DMA，板端端到端
  PASS（硬件分数 0.997878 vs numpy 0.997876，conv1 最大误差 0.001838）。

这一正一反两条经验说明：模板的价值不在于"一定让你上硬件"，而在于把"哪部分值得搬、
哪部分不值得搬"用计算量和工程量摆到台面上。

## 失效条件

- 算法步骤本身没定：模板会给出看似完整但不可执行的划分。
- 没有资源约束：模型会假设资源充足，给出无法收敛的方案。
- 要求它"保证加速比"：任何没有依据的加速比都不要写进报告；只接受能给出计算过程的估计。
- 算法数据量极小（如每帧只有几十个样本）：PL 的启动与传输开销会吃掉全部收益，
  此时模板通常会（也应该）建议留在 PS。
- **计时口径未对齐**：PL 侧耗时只算 HLS 核 `ap_start→ap_done`，不含 DMA/cache/量化；
  与 PS 对比时必须两端都用同一口径（都只算纯计算，或都算端到端），否则加速比不可信。
