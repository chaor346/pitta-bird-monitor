# 案例模板：事件触发 → 响应 的多模态状态机

**类型**：工程模板（case template）
**适用场景**：一个进程（或一块板卡的一部分）检测到事件后，通知另一个进程去做较重的处理。
例：鸟鸣触发拍照、枪声触发录像、关键词唤醒后启动识别、传感器越限后启动采集。
**不适用**：需要硬实时（微秒级）闭环的场合——文件/进程间通知的延迟在毫秒到几十毫秒量级。

---

## 状态机

```
          ┌──────────────┐
          │   WAITING    │  等事件
          └──────┬───────┘
                 │ 检测到触发（文件出现 / 队列消息 / 信号）
                 ▼
          ┌──────────────┐
          │  SEARCHING   │  处理中（识别/搜索），受 search_sec 限制
          └──┬────────┬──┘
   找到目标 │        │ 超时
             ▼        ▼
       ┌──────────┐  ┌──────────────┐
       │ RECORDING│  │ 回到 WAITING │
       └────┬─────┘  └──────────────┘
             │ 目标消失（连续 N 次无目标 且 跨度 ≥ M 秒）/ 超时保护
             ▼
          WAITING
```

## 参数表（照抄后按场景调）

| 参数 | 含义 | 取值建议 | 调错的后果 |
|------|------|----------|-----------|
| `threshold` | 事件判定的置信度阈值 | 0.5 起，按误报率调 | 太低满屏误触发；太高漏检 |
| `min_hits` | 连续命中次数 | 2 | 1 时单帧噪声即触发 |
| `cooldown` | 两次触发最小间隔 | 30 s | 太小重复触发同一事件 |
| `search_sec` | 处理阶段超时 | 30 s | 太小刚进入就退出；太大卡住不返回 |
| `absence_hits` | 连续无目标次数 | 推理慢时取 2–3 | 太小提前结束；太大录像拖长 |
| `absence_sec` | 首次与末次无目标的时间跨度 | 2–6 s | 同上 |
| `vision_timeout` | 无新鲜结果的强制退出时长 | 2× 单次推理耗时 | 太小误判；太大挂死 |

## 触发通道的三条硬规则

1. **一次事件一次消费**：响应端检测到后立即删除（或重命名），否则文件存在性会被反复当成新事件。
2. **两端路径必须显式且一致**：用命令行参数传绝对路径，不要依赖各自 CWD。
3. **通知要带载荷**：写入 `score=0.9142 time=1792345678` 这类内容，便于事后追责与调阈值。

## 反向通道（可选但强烈建议）

响应端在重负载期间（如录像编码）需要告诉检测端"先别推理"，否则两者抢 CPU：

- 响应端开始重负载 → 创建 `vision_recording.lock`；
- 响应端结束 → 删除该文件；
- 检测端看到锁存在 → 暂停推理，但**继续采集**（不能停采集，否则漏掉事件）。

用"文件存在 + 内容含 PID"的方式，可以避免进程崩溃后留下永久锁。

## 自检方法

1. 手动 `touch` 触发文件，确认响应端状态切换日志正确；
2. 连续 touch 两次，确认第二次不会因为文件残留而重复处理；
3. 把 `search_sec` 调到 1 s，确认超时路径能回到 WAITING；
4. 杀掉响应端进程，确认检测端不会因为锁残留而永久暂停；
5. 用 `time.monotonic()` 记录"写触发 → 响应端首次处理"的延迟，作为通信延迟指标。

## 已验证效果

本项目（鸟鸣 → 图像识别）实测：触发文件写入到图像端检测到，延迟 **< 100 ms**；
手动造触发文件可稳定复现状态切换；锁文件机制使录像期间的音频推理暂停生效。

## 失效条件

- 两端挂在不同的文件系统/容器里：绝对路径也不通，需要换成 socket 或消息队列。
- 事件频率高于处理能力：会堆积；必须靠 `cooldown` 或队列长度上限丢弃。
- 需要亚毫秒级响应：文件轮询不合适，应改为中断或共享内存 + 事件标志。
