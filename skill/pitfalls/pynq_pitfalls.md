# PYNQ / Zynq 踩坑清单

本清单按「触发条件 → 现象 → 定位步骤 → 根因 → 修法 → 来源」组织，全部来自
`pitta_bird_monitor`（PYNQ-Z2 + INMP441 + AXI DMA + USB 摄像头）开发过程中的真实失败。
凡未在本项目上复现的条目都标注「推断」，请自行验证后再引用。

分三类：
- A. 硬件与接口（板级、电平、时序、采样）
- B. PS 侧软件（DMA 驱动、缓存、线程、数值格式）
- C. 系统协同（多进程触发、状态机、资源争抢）

---

## A. 硬件与接口

### A1. INMP441 的 L/R 引脚悬空 → 采集数据全 0

- **触发条件**：INMP441 模块 L/R 引脚未接 GND 也未接 VDD，直接悬空。
- **现象**：DMA 正常传输、状态位正常、WAV 里全是 0；任何阈值都判不出声音。
- **定位步骤**：
  1. 采 3 包数据打印 RMS，若左右声道都恒为 0，先怀疑硬件而不是软件；
  2. 万用表蜂鸣档测 L/R 到 GND 是否导通；
  3. 对照模块丝印确认 L/R 是否已有内部下拉/上拉。
- **根因**：L/R 决定 I2S 输出哪个通道；悬空时输出驱动器处于未定义状态，SD 恒低。
- **修法**：L/R 接 GND（左声道）或 VDD（右声道），不要悬空。
- **来源**：本项目首次上板，采集全 0；接 GND 后立刻恢复。

### A2. 24 bit 音频用 `& 0xffffff` 解码 → 负样本失真

- **触发条件**：硬件已把 24 bit 符号扩展到 32 bit，软件又按无符号 24 bit 截取。
- **现象**：波形看起来"有声音"，但鸟鸣置信度整体偏低，负样本（静音段）尤其异常。
- **定位步骤**：打印同一段数据的 `raw.astype(np.int32)` 最小/最大值；若全为正数说明符号位丢了。
- **根因**：`& 0xffffff` 把符号位抹成 0，负半周变成接近满量程的正值。
- **修法**（二选一，结果等价）：① 直接 `raw / 2**23`（硬件已符号扩展）；② 现行板端实现——
  先 `& 0xffffff` 取 24 bit，**再按 bit23 符号扩展**（`if u & 0x800000: u -= 0x1000000`），
  然后 `/256` 转 int16 PCM（codec 只吃 PCM16）、再 `/32768` 转 float。
  **只掩码不补符号扩展**才是错的；也不要左移 8 位。
- **来源**：本项目音频模型准确率异常，改解码方式后恢复。

### A3. I2S 左右声道物理顺序不确定

- **触发条件**：不同 INMP441 模块/接线方式下，WS 极性与声道对应关系不一致。
- **现象**：其中一个声道有信号，另一个几乎为 0，但"哪个是左"因板而异。
- **定位步骤**：分别计算左右声道 RMS，取大者；或播放已知单声道测试音观察哪一路有能量。
- **根因**：模块丝印与 I2S 规范的 WS=0/1 对应关系不统一。
- **修法**：运行时按 RMS 选声道，并把两路都存下来核对，而不是写死 `[:,0]`。
- **来源**：本项目 `inmp441_record.py` 自动选声道（实测 L=753545 量级，R 明显更小）。

### A4. 采样率不对 → 频谱整体偏移

- **触发条件**：Overlay 下载后没有显式设置 FCLK，或 I2S 分频参数与 32 kHz 不匹配。
- **现象**：录到的鸟鸣听起来"变调"，mel 特征与训练集分布不一致，准确率下降。
- **定位步骤**：录 1 kHz 标准音，用零交叉或 FFT 测实际频率；同时读 `Clocks.fclk0_mhz`。
- **根因**：PL 侧分频基于 FCLK，FCLK 与设计假设不一致时采样率同比缩放。
- **修法**：下载后显式 `Clocks.fclk0_mhz = 100.0`，并在报告中声明该值。
- **来源**：本项目 `inmp441_record.py` 在 Overlay 之后立即设置 FCLK0。

### A5. Pmod 电平与上拉

- **触发条件**：INMP441 数据线长、或模块无内部下拉。
- **现象**：偶发数据错位/噪声，重启后时好时坏。
- **定位步骤**：示波器看 SD 空闲电平；或在 XDC 加内部下拉后对比误码率。
- **根因**：SD 空闲时高阻，长线引入耦合。
- **修法**：XDC 中给 SD 加 `PULLDOWN true`，模块侧最好外接 100 kΩ 下拉。
- **来源**：本项目 `inmp441_pmodb.xdc` 已加内部下拉作为兜底。

## B. PS 侧软件

### B1. DMA 寄存器偏移靠记忆/博客 → 全部错位

- **触发条件**：从教程或别的工程复制 `S2MM_CR=0x30` 一类偏移，但 IP 版本或通道配置不同。
- **现象**：写寄存器无反应、状态位恒 0、DMA 永不启动，且没有任何报错。
- **定位步骤**：读 `.hwh` 的寄存器表，与代码里的偏移逐个对照（`hwh_probe.py --audit`）。
- **根因**：AXI DMA 的偏移随是否使能 SG、使能哪些通道而变化。
- **修法**：偏移一律从 `.hwh` 生成（`hwh_probe.py --emit-driver`），不要手抄。
- **来源**：本项目最早一版驱动手抄偏移，`hwh_probe.py --audit` 现已对账通过（10 处全命中）。

### B2. 寄存器存在 ≠ 通道存在

- **触发条件**：只使能 S2MM（`C_INCLUDE_MM2S=0`），但代码里仍去读写 MM2S 寄存器。
- **现象**：MM2S 读写"成功"但值不变（读回复位值），误判为"DMA 挂死"。
- **定位步骤**：看 `.hwh` 中 `C_INCLUDE_*` 参数与寄存器 `IS_ENABLED` 的组合。
- **根因**：IP 的寄存器表按固定模板列出，未实现的通道仍占位；部分版本 `IS_ENABLED` 仍为 true。
- **修法**：以 `C_INCLUDE_*` 参数为准判断通道是否存在；`hwh_probe.py` 会自动告警。
- **来源**：本项目 `.hwh` 实测：`C_INCLUDE_MM2S=0`，而 `MM2S_DMACR/MM2S_DMASR/MM2S_SA` 标记启用。

### B3. S2MM_LENGTH 写的是字节数，不是 beat 数

- **触发条件**：按"样本数"或"beat 数"写长度寄存器。
- **现象**：传输完成但只收到 1/4 数据（32 bit 样本时），或长度不对导致越界写。
- **定位步骤**：比对"申请缓冲字节数 / 实际写入字节数 / 收到的 beat 数"三者关系。
- **根因**：LENGTH 以字节计；且写入值需与实际缓冲大小一致。
- **修法**：`length = beats * 4`（32 bit 通路），并在接收后读回 LENGTH 的低位作为实际字节数。
- **来源**：本项目 `recv_packet(mmio, buf, PKT_BEATS * 4)`。

### B4. 缓冲区 cache 未维护 → 数据"没到"或"到了是旧值"

- **触发条件**：`allocate(... cacheable=True)` 后直接读，或发送前没有 flush。
- **现象**：DMA 明明完成，CPU 读到的仍是预填值；或发送出去的是缓存里的旧数据。
- **定位步骤**：预填已知模式 → 传输 → `invalidate()` → 统计被覆盖字数（`dma_selftest.py` 的做法）。
- **根因**：ARM 的 D-cache 与 DMA 看到的内存不一致。
- **修法**：发送前 `flush()`，接收后 `invalidate()`；地址必须用 `physical_address`。
- **来源**：本项目 `inmp441_record.py` 每包 `buf.flush()` / `buf.invalidate()`。

### B5. `signal` 只能在主线程设置 → 采集与推理抢线程时崩溃

- **触发条件**：在子线程里注册信号处理函数做超时控制。
- **现象**：`ValueError: signal only works in main thread`，或偶发直接退出。
- **定位步骤**：看 traceback 是否落在子线程的 signal 调用。
- **根因**：CPython 限制。
- **修法**：采集放主线程、推理放子线程；超时用 `time.monotonic()` 轮询而不是信号。
- **来源**：本项目早期版本在子线程用信号做超时。

### B6. 忙等轮询状态位 → CPU 打满、推理更慢

- **触发条件**：`while not (sr & IOC): sr = read()` 中间没有 sleep。
- **现象**：单核占用 100%，与图像推理互相拖慢，端到端延迟抖动大。
- **定位步骤**：`top` 看 python 占用；对比加 sleep 前后的推理耗时分布。
- **根因**：MMIO 读本身有延迟，空转消耗调度时间片。
- **修法**：轮询里加 1–2 ms `time.sleep()`；或改用中断（需 PL 侧接 IRQ）。
- **来源**：本项目 `recv_packet` 用 `time.sleep(0.002)`。

### B7. 不检查 DMA 错误位 → 静默丢数据

- **触发条件**：只等 IOC 位，不看 DMAIntErr/DMASlvErr/DMADecErr（bit4/5/6）。
- **现象**：偶发包内容错乱或变短，日志里没有任何错误。
- **定位步骤**：每次传输后读 SR，把 0x70 掩码结果打进日志。
- **根因**：错误发生后 IOC 仍可能置位，看起来"成功"。
- **修法**：`if sr & 0x70: raise`，并打印原始 SR；`dma_selftest.py` 已内置该检查。
- **来源**：本项目 `recv_packet` 中的 `SR_ERRBITS` 检查。

### B8. 软复位未等完成就重配

- **触发条件**：写完 `CR.Reset` 立刻继续配置。
- **现象**：DMA 拒绝启动，或寄存器写入被忽略。
- **定位步骤**：读 CR 看 Reset 位是否还在；加入超时打印。
- **根因**：软复位需要若干时钟周期。
- **修法**：写 Reset → 轮询 CR.Reset 清零（带 2 s 超时）→ 再 Run。
- **来源**：本项目 `reset_dma()`。

## C. 系统协同

### C1. 触发文件写了不删 → 重复触发

- **触发条件**：响应端只检测文件存在，不删除。
- **现象**：一次鸟鸣触发后，录像反复启动；或状态机卡在 SEARCHING。
- **定位步骤**：`ls runtime/trigger/` 看文件是否残留；加日志打印"检测到/已删除"。
- **根因**：文件存在性是电平信号，不是事件。
- **修法**：检测到即删除（或用"读后重命名"），保证一次事件一次消费。
- **来源**：本项目触发协议规定响应端必须先删再处理。

### C2. 两端路径不一致 → 永远收不到触发

- **触发条件**：两端用不同的相对路径/不同用户的家目录启动。
- **现象**：音频端打印 TRIGGER，图像端毫无反应。
- **定位步骤**：两端各打印 `os.path.abspath(trigger)`；用 `touch` 手动造一个文件验证。
- **根因**：相对路径依赖各自的 CWD。
- **修法**：命令行显式传绝对路径，启动脚本里统一 `BASE_DIR`。
- **来源**：本项目 `--vision-trigger` / `--audio-pause-file` 参数显式传递。

### C3. 推理结果过期被当成"目标离开" → 录像提前结束

- **触发条件**：推理比帧率慢，队列里积压旧结果。
- **现象**：鸟还在画面里，录像却结束了；或刚结束又重新开始。
- **定位步骤**：给每条推理结果带时间戳，打印"结果时间 vs 当前时间"的差值。
- **根因**：把"没有新结果"误判成"没有目标"。
- **修法**：新鲜度超时的结果直接丢弃，且不能计入 `misses`；只有"新鲜且判无目标"才累加。
- **来源**：本项目存在性录像要求"推理过期必须清零计数，不能当目标离开"。

### C4. 推理与录像抢 CPU → 延迟暴涨

- **触发条件**：A9 双核同时跑 numpy 推理 + 编码写盘。
- **现象**：录像期间音频推理从 1.5 s 拖到数秒，可能漏检整段鸟鸣。
- **定位步骤**：分别记录"只有推理"和"推理+录像"时的单次耗时分布。
- **根因**：两个进程都吃满核，且 numpy 在多线程下争抢。
- **修法**：录像期间用锁文件暂停音频推理，录完恢复（本项目 `av_recording_lock.py`）。
- **来源**：本项目 `vision_recording.lock` 协议。

### C5. 摄像头权限

- **触发条件**：非 root 运行，`/dev/video0` 属 root:video。
- **现象**：`cv2.VideoCapture(0)` 打不开，或只返回空帧。
- **定位步骤**：`ls -l /dev/video0`；`id` 看当前用户组。
- **根因**：设备节点权限。
- **修法**：`sudo` 运行，或把用户加入 `video` 组；脚本里可先 `chmod 666 /dev/video0`。
- **来源**：本项目 `board/start_vision.sh` 中显式 chmod。

### C6. 固定时长录像浪费存储且录不全

- **触发条件**：不论目标是否在场，固定录 N 秒。
- **现象**：大量空画面；或目标停留超过 N 秒被截断。
- **定位步骤**：统计"有效帧占比 = 含目标帧 / 总帧"。
- **根因**：目标停留时间不可预知。
- **修法**：改为存在性录像（见 `templates/presence_recording.md`）。
- **来源**：本项目对比固定 10 s 与存在性录像的有效内容占比，后者高 5–10 倍（估算）。

## D. HLS 加速器上板（PL 侧计算核 + AXI-Stream + DMA）

> D 类来自把一个 Vitis HLS 综合出的 GEMM 核（`gemm_top`，3 路 DMA：A/B 进、C 出）
> 从 PC 仿真搬到 PYNQ-Z2 上板的全过程。任何"PL 侧放一个 HLS/RTL 计算核，PS 侧通过 DMA
> 喂数据、收结果"的工程都会遇到这组问题。

### D1. HLS stream 末拍缺 TLAST → S2MM 永不置 IOC

- **触发条件**：HLS 生成的 AXI-Stream 输出在最后一个 beat 没有拉 `TLAST`。
- **现象**：DMA `recvchannel.transfer(buf)` 返回后，DMASR 的 IOC 位始终不置位；
  缓冲里其实已经有数据，但通道状态停在 Running，下次再 transfer 会报错或挂死。
- **定位步骤**：
  1. 传输后读 `dma.recvchannel._mmio.read(0x04)`（DMASR），看 bit12（IOC）是否为 1；
  2. 用 `buf` 里的实际数据是否合理判断"数据其实已经到了"；
  3. 在 HLS 源码里检查输出循环最后一拍是否显式给 `last` 信号。
- **根因**：AXI DMA 的 S2MM 通道靠 TLAST 判断"一帧结束"；没有 TLAST，它一直等下去。
- **修法**：
  - 根本：HLS 设计里给 stream 末拍拉 TLAST（新版 Vitis HLS 对 `hls::stream` 的显式
    `last` 信号支持更完整）；
  - 兼容旧 bit：不要把 S2MM IOC 作为"完成"判据；改用 HLS 核 `ap_ctrl` 的
    `ap_done`（bit1）作为计算完成权威判据，S2MM 缺 IOC 时 `stop()` → sleep 2ms →
    `start()` 复位通道以便下次复用。
- **来源**：本项目 `gemm_board.py` 注释明确写了"旧 bit 缺 TLAST"，`e2e_board.py`
  的 `GemmConv1._ensure_s2mm_idle()` 即此兼容路径。

### D2. AXI DMA 单次传输 16 KB 上限 → 大矩阵 transfer 失败

- **触发条件**：DMA IP 默认 `c_sg_length_width=14`，单次最多传 2^14 = 16384 字节；
  而实际缓冲远大于此（本项目 C 缓冲 = 12864×16×2 = 411 KB）。
- **现象**：`transfer(buf)` 要么直接抛异常，要么静默只搬前 16 KB，后面全是旧值。
- **定位步骤**：
  1. 板端读 `dma.recvchannel._size`（PYNQ 报的单次上限）；
  2. 算实际缓冲 `buf.nbytes`；若 `cap < need`，就是这个问题；
  3. 在 hwh 里 `grep C_SG_LENGTH_WIDTH`，值为 14 即默认旧配置。
- **根因**：DMA IP 的描述符长度位宽决定单次传输上限，不是 PYNQ 的问题。
- **修法**：在 Vivado 里把 AXI DMA IP 的 `c_sg_length_width` 改成 23（单次可传 8 MB），
  重新综合、重新下 bit；板端 `_size` 应报 8388608。启动脚本里加一道 FATAL 检查：
  `if cap < need: 报错并提示重新覆盖 bit/hwh`。
- **来源**：本项目 `gemm_board.py` 第 200–209 行即此 FATAL 检查；hwh 里
  `C_SG_LENGTH_WIDTH=23` 是新版指纹。

### D3. PYNQ DMA 默认等中断，中断线没接好 → transfer 永久挂死

- **触发条件**：块图里 DMA 的中断输出没连到 PS 的 IRQ，或连错了线；PYNQ 的
  `sendchannel/recvchannel.transfer()` 默认走中断等待。
- **现象**：`transfer(buf)` 之后 `wait()` 永远不返回；CPU 占着一个核空转。
- **定位步骤**：
  1. 在 `transfer` 前后加打印，确认卡在 wait 而不是卡在数据准备；
  2. `top` 看 python 是否单核 100%；
  3. 在 PYNQ 里读 `ol.ip_dict['axi_dma_0']['interrupts']`，看是否为空。
- **根因**：PYNQ 的 DMA 封装在构造时会尝试注册中断回调；中断线没接对时回调永远不来。
- **修法**（二选一）：
  - 正确做法：块图里把 DMA 的 `irq` 接到 `processing_system7_0/pl_ps_irq0`，重新综合；
  - 快速做法（本项目采用）：环境变量 `os.environ["PYNQ_DISABLE_DMA_INTERRUPT"]="1"`，
    并在 Overlay 之后清空每个 IP 的中断描述
    `for _n,_d in ol.ip_dict.items(): if _d.get("interrupts"): _d["interrupts"]={}`，
    然后自己用寄存器轮询 DMASR 判断状态。
- **来源**：本项目 `gemm_board.py` 第 27、143–145 行。

### D4. Overlay 下载后 FCLK 未显式设置 → 时钟不是设计假设的频率

- **触发条件**：Overlay 下载后直接启动硬件，不显式设置 PL 时钟。
- **现象**：HLS 核行为异常、采样率不对、时序不收敛；同样的设计在别人板上能跑、
  在自己板上速度不对。
- **根因**：PYNQ Overlay 下载后 FCLK 可能沿用上次设置或默认值，不一定是设计假设的
  100 MHz。
- **修法**：Overlay 之后立即 `from pynq.ps import Clocks; Clocks.fclk0_mhz = 100.0`，
  并在日志里打印该值，作为复现条件的一部分。
- **来源**：本项目 `gemm_board.py` 第 139 行、`e2e_board.py` 第 174 行；
  与 A4（采样率）是同一类问题在 PL 时钟侧的表现。

### D5. bit/hwh 版本不一致 → 板上跑的不是以为的那个

- **触发条件**：改了硬件重新综合，scp 到板子后没覆盖成功（路径错、权限错、
  Python 进程缓存了旧 overlay）。
- **现象**："我明明改了 TLAST 怎么还是不置 IOC"——因为板上根本是旧 bit。
- **定位步骤**：
  1. 板端 `md5sum gemm_soc.bit gemm_soc.hwh`，与 PC 端对比；
  2. hwh 里 `grep C_SG_LENGTH_WIDTH`，应为 23；
  3. 文件大小是否对得上（本项目最终版 hwh = 586046 字节，旧版 586492）。
- **根因**：部署链路没有版本指纹；PYNQ Overlay 在同一 Python 进程里加载过一次后
  不会自动重读文件。
- **修法**：
  - 板端启动脚本里硬编码期望 MD5，不一致就 FATAL 退出；
  - 覆盖文件后必须**断电重启板子或重开 Python 进程**；
  - `verify_board.sh` 做一次纯文件自检（不加载 bit），作为上板第一道门。
- **来源**：本项目 `verify_board.sh`、`gemm_board.py` 第 152–186 行的 MD5 自检。

### D6. DMA IOC ≠ 计算完成，ap_done 才是权威判据

- **触发条件**：把"DMA 收完了"当成"HLS 核算完了"。
- **现象**：读出来的 C 缓冲是半成品（最后几拍还没算完），或 IOC 还没置位但
  ap_done 已经亮了，逻辑顺序混乱。
- **根因**：DMA IOC 只表示"数据从 stream 搬到了内存"；HLS 核内部可能还有后续流水
  级没排空。反过来，新 bit TLAST 修对后 S2MM 会正常置 IOC，但 HLS 核的 ap_done
  仍需单独等。
- **修法**（固定顺序）：
  1. 先武装 S2MM：`dma_C.recvchannel.transfer(bufC)`；
  2. 启动 MM2S：`dma_A.sendchannel.transfer(bufA)`、`dma_B.sendchannel.transfer(bufB)`；
  3. 写 `ap_ctrl = 0x1` 启动 HLS 核；
  4. 等两路 MM2S `idle`（输入发完）；
  5. 轮询 `ap_ctrl` bit1（ap_done）作为计算完成权威判据；
  6. 检查 S2MM IOC（新版应置位；旧版缺 TLAST 走 D1 兼容路径）；
  7. `bufC.invalidate()` 后再读。
- **来源**：本项目 `gemm_board.py` 主流程第 228–250 行、`e2e_board.py GemmConv1.run()`。
